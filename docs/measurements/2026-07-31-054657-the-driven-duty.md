# The driven duty, measured rather than derived · 2026-07-31 05:46:57

[The previous record](2026-07-31-050322-the-agent-side-of-a-session.md) measured an agent CLI at 0.112 cores over its lifetime, noted that the figure belongs to a session waiting on a human, and reasoned its way to about 0.42 for a harness-driven one. It labelled that step *arithmetic on measured numbers rather than a measurement, and a harness would settle it*.

No harness was needed. This loop has been driving one session continuously for the last forty-two minutes, which is the condition a harness makes.

## Two routes, and they agree

| Route | Method | Duty |
|---|---|---|
| **Lifetime counter, differenced** | 679 CPU-seconds over 2,557 wall seconds between the previous record's reading and now | **0.266** |
| **Live sampler** | running mean from one origin, resampled every 30 s for 601 s | **0.273** |

**2.6% apart**, from a counter Windows has been incrementing since the process started and from a sampler that knows nothing about it. [The agreement is the check](../../CLAUDE.md) — a repeat would have said the number is stable, and two routes say it is the number that was meant.

**The derived 0.42 was too high by 58%.**

## Three regimes, not two

| | Cores | What it is |
|---|---|---|
| Waiting on a human | 0.112 | a day of ordinary use, mostly idle |
| **Driven by a loop** | **0.27** | **what a harness produces** |
| Inside a turn, instantaneous | 0.42 | three 20 s windows during active generation |

The derivation assumed a driven session sits in the third row. It sits in the second, and the mechanism is visible in the sampler: **`cargo clippy` ran during one interval and the reading moved 0.229 → 0.252.** A build that saturated several cores barely touched the CLI, because the work was in `cargo.exe`.

So a driven session is inside a turn about **64%** of its wall time rather than all of it. The rest is model latency, which is served elsewhere, and tool execution, which is charged to a child process.

## What that moves

`redline = 2ηC/d` with [the corpus's own constant `2ηC ≈ 25`](2026-07-30-154348-duty-is-derivable.md):

| `d` | Core ceiling | |
|---|---|---|
| 0.112 | 223 | an idle session's headroom |
| **0.27** | **93** | **measured** |
| 0.42 | 59 | the derived figure this replaces |

## The engine ceiling of twelve leaves out the agent

[Twelve](2026-07-31-045604-an-error-bar-for-the-engine.md) is `21.97 ÷ 1.87`, and 1.87 GiB is the engine. The same corpus establishes that [the agent CLI is the floor the engine lands on](2026-07-31-050322-the-agent-side-of-a-session.md) and never subtracts it from the budget.

A cooking session holds both:

| | Per session |
|---|---|
| Engine, cooking | 1.87 GiB ± 6.4% |
| Agent CLI | 0.52 GiB |
| **Together** | **2.39 GiB** |

`21.97 ÷ 2.39` is **9.2 sessions**, and the engine's error bar puts it between **8.8 and 9.7**.

**Nine, not twelve.** That is arithmetic on two measured numbers rather than a third measurement, and it is the same class of gap the previous record found one level up: each half was measured carefully and the sum was never taken.

**It was not even for want of writing them down together.** [`sessionbench`'s own README](../../sessionbench/README.md#what-we-measure-against) already adds the two to argue a pseudoconsole costs 0.35% of a session — it built the denominator, used it once, and no artifact divided the budget by it. Nothing here contradicted anything; a figure simply lived in one file and was needed in another.

## Resident memory is a sawtooth, not a climb

The previous record read 559–586 MiB and caveated it as *closer to a ceiling than a typical value* because resident state grows with a session's history. Ten minutes of sampling the same process gives **480 to 541 MiB**.

It went down. A context compaction happened between the two readings and released roughly 80 MiB, after which it began climbing again — 480 at the probe's start against 541 near its end.

**So the caveat was right and is now measured.** The session's resident cost oscillates rather than growing monotonically, and 0.580 GiB was near a peak. The memory ceiling on the agent alone moves between **37 and 42 sessions** across that band, which leaves the design figure of 38 conservative and intact.

## What this rests on

- **One CLI, one machine.** Claude Code driving a Rust repository, not a generation session driving an engine. A session holding an engine's worth of conversation would hold more.
- **The sampler's readings are a running mean from one origin**, not independent windows — they converge rather than scatter, so they are one route rather than twenty samples.
- **The 0.52 GiB used in the combined ceiling is this session's post-compaction figure.** Taking the pre-compaction 0.58 instead gives 8.9 rather than 9.2, which does not change the answer to the nearest session.
- **`2ηC ≈ 25` was measured on synthetic sessions on this machine.** Applying it to a heterogeneous agent-plus-engine session assumes the relation carries across, which no measurement here has tested.
