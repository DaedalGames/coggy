# What an engine session holds between builds · 2026-07-31 03:51:11

Every engine reading before this one measured a session mid-compile. That is the peak, and a generation session compiles for part of a turn and waits on a model for the rest — so the peak got measured and called the session.

## The reading

`TP_Blank` built once, then held.

| | While building | After |
|---|---|---|
| **RSS** | **3.27 GiB peak** | **8.97 MiB** |
| Processes | 9 | 1 |
| conhost | 3 | 0 |

**An engine build leaves nothing behind.** `cl.exe`, `link.exe` and UnrealBuildTool exit and take their memory with them, and what remains is the shell holding the session's place — 8.97 MiB of `cmd.exe`. **That is the engine's half of a session and not the session**: [the agent CLI driving it holds 580 MiB throughout](2026-07-31-050322-the-agent-side-of-a-session.md), which is the floor this figure sits on.

A hundred *engines* at rest come to 897 MiB. A hundred sessions come to that plus [58 GiB of agent CLI](2026-07-31-050322-the-agent-side-of-a-session.md), which is what actually meets the 21.97 GiB budget.

## Which reverses the reversal

Two records ago, an Unreal session holding 1.69 GiB steady put the RSS condition at thirteen sessions and [overturned M0's conclusion that memory was slack](2026-07-31-022200-an-unreal-session.md). That figure was taken from a session building continuously, which is a state a session is in for part of a turn — and [only one session can be in it at a time anyway](2026-07-31-034150-unreal-builds-serialise.md).

So the three engine readings settle into one account:

| | Cost | Binds? |
|---|---|---|
| Session at rest | 8.97 MiB | No, by three orders |
| Session compiling | up to 3.27 GiB | Transient, and serialised |
| Compiling concurrently | one at a time per engine installation | **This is the constraint** |

**Neither memory nor cores is what stops a hundred engine sessions. The build queue is.** Memory and cores were measured against the moment a session is least like itself.

## What the sampler could not tell us here

`timeout /t 5` returns immediately when stdin is not a console, so the idle half of this workload span at fifty iterations a second rather than waiting. **The RSS figure survives that** — a spinning `cmd.exe` is about nine megabytes, which is what was measured, and the session holds nothing beyond it. The cores figure does not: 0.42 is the spin loop, not a session waiting on a model.

That leaves the cores an engine session costs while idle unmeasured, and it is almost certainly near zero — a process blocked on a socket burns nothing. It is recorded as unmeasured rather than assumed.
