# Working rules

[ROADMAP.md](ROADMAP.md) says what to build next and [docs/PLAN.md](docs/PLAN.md) says why. **This file owns how to work**, and deliberately repeats nothing those two already hold.

## Never build what already exists

The rule broken most often here, because writing code feels like progress and reading someone else's does not. A clean-room implementation of a solved problem is a defect, not craftsmanship — and the tell is that it arrives with no citation.

Before writing any non-trivial module, in this order:

1. **Read this repository's own reference list first.** [ROADMAP's milestones](ROADMAP.md#sequencing-direction) name what each one consumes before what it writes, and [sessionbench's prior-art table](sessionbench/README.md#what-we-take-from-prior-art) names what the benchmark takes from whom. Both were written by someone who had already done the survey. Opening a web search before reading them repeats work that is sitting in the repo, and can talk you past a decision the repo already made.
2. **Then search outward, for the mechanism rather than the goal.** The list says *what* to consume; a search is for *how*. What you need rarely appears under the name of the problem — the platform has usually already solved it under the name of something else.
3. **Check the licence.** MIT, Apache-2.0, BSD, MPL: depend on it or vendor it. GPL: fine, we are GPL-3.0-or-later. Anything that cannot reach us: read it, then rebuild the logic from its description rather than its source.
4. **Take the largest piece that fits** — the crate, then the module, then the algorithm, then the CLI shape, in that order of preference. Customising something we took is good. Not having looked is not.
5. **Cite what you took**, in the code comment and the commit body, including what you changed and why.

**The reliable tell** is writing a data structure to track something the operating system already tracks. Process membership, memory accounting, and lifetime are all kernel bookkeeping, and a hand-rolled version of any of them is a bug waiting for a long enough run.

**The rule is retroactive.** It governs code already here, not only code about to be written, and "we already built it" is the weakest argument available — the work is sunk either way, and keeping the worse version costs from here on. Finding that something in this repository duplicates a maintained project is a reason to delete ours.

Keeping ours is allowed, and it needs a **specific** reason recorded next to the code: the thing the alternative gets wrong, in its own words where possible. "Similar to GitHub's anchors" is a reason; "ours is more tailored" is not. And a rejection is rarely total — take the part that fits and say which part you did not.

The same rule governs what we *do not* consume: [PLAN's anti-patterns](docs/PLAN.md#anti-patterns-these-kill-the-project) name the places where building it ourselves kills the project.

## Measure before you optimize

The project's own reason for existing. [M0](ROADMAP.md#current-priority-m0--attribution) is a measurement milestone precisely because a daemon built around an unmeasured assumption reproduces the lag it exists to remove.

- A performance claim without a `sessionbench` artifact is not a claim.
- **And the artifact holds more than its report does — read the samples before building an instrument.** One night produced six findings and five came from columns written to every `samples.jsonl` for days and never read: `cpu_percent` gave what a run really held and the 18% of samples one hold lost the machine for, `work_units` over the same intervals said those dips were real rather than a sampler artifact, `available_memory_bytes` said 1.65 GiB went missing alongside them, `processes` said no session had exited, `defender_cpu_percent` ruled Defender out, and `output_bytes` said filling the scrollback costs the sessions nothing. **A report summarises; the samples are the measurement** — and a mean in a report hid an interruption that was read as an 11% property of the workload for three hours. **And before querying a column, check what [`observe.rs`](sessionbench/src/observe.rs) does with it**, because the guards it carries are exactly the ones an ad-hoc read loses. Four findings on 2026-08-11 were derived by reading `concurrent-samples.jsonl` directly and all four were artifacts that file already handles: three treated `work_units` as a per-sample series when a **daemon-backed** hold resolves it at `REPORT_EVERY` 10 s against a 5 s interval, and one anchored a window at a hold's start, where the opening report counts elapsed time in full and work only partly. `observe.rs` integrates over a window's own span rather than reading single ticks, and filters work-rate windows by a 30-second `STARTUP_WINDOW` — **which covers the report period by luck**, having been widened for a single-core boost transient nine days earlier: *six is what has to be excluded; thirty is what is*. Of seven instrument changes made the same night, three were answerable from what was already recorded, and one was a counter built, measured and reverted once [the bracket's own solo rungs turned out to separate the states it was meant to detect](sessionbench/src/host.rs).
- **Where a deciding figure is written decides whether it survives.** Three shapes turned up in one day. A figure that justified a design and lived only in a task note — the 8.5% behind bracketing, the 581.6 MiB behind "the tool runs at a hundred" — goes when the task closes, and the design stays without it. A figure written only beside the constant it set survives, but nothing else can reach it: `MIN_SAMPLES_PER_RUNG`'s starved-sampler run has no record, and its artifacts are pruned. And a figure that *is* recorded still needs the thing it decided to point at it, or the stronger evidence goes uncited while the weaker one gets quoted — PLAN cited where `2ηC/d` was derived while claiming it had been checked elsewhere. **The check is mechanical**: grep the repository for the figures a rule or a constant leans on, and for records nothing outside the index cites.
- **Every measured improvement gets a record with an as-is column beside the to-be one.** The as-is column is what makes it a measurement rather than an announcement. It belongs in [docs/measurements/](docs/measurements/) as `YYYY-MM-DD-HHMMSS-<slug>.md`, stamped with the moment the record was committed rather than the moment the run happened — a clock the next clone can still read, so the records sort into the order they were written on any machine. Publish it — an engineering figure has no reason to be private. Keep `.local` for what genuinely cannot be, which so far is unit economics and funding posture and nothing else.
- **A record is a log, and rewriting a log stops it being one.** Every other artifact here gets refreshed until it says what is true now; a measurement record says what was true when it was taken, including what it could not do yet. When a record's open question gets answered, **date the claim and append the answer** rather than replacing it — an attempt to swap *nothing checks this* for *this is checked* left one paragraph asserting both. What a run found, and what nobody had built at the time, are the same kind of fact.
- **A verdict is not evidence — record the figure it was computed from.** Twice in one file: `hold.json` said `dropped_output: held` with the failed-read count that decided it thrown away, and `work_rate: broke` with the slowdown behind it living only in a sibling artifact. Both read as measurements and neither could be recomputed, which matters most where the passing value is zero or the condition is a ratio nobody else holds. **Make the figure travel with the verdict**, and make an absent figure carry an absent verdict — `None` beside `NotTaken` cannot come apart, where a `0.0` beside `Held` silently can.
- **A KPI that restates an existing record is a view of it, not a second record.** Fold what is new — usually the cost of the change — into the record that owns the measurement, and do not create the file.
- **Reach the same number twice by different routes, and the agreement is the check.** It keeps catching things: `η` above 1 said the core count was physical where the measurement was logical; one session's average over time matching four sessions' total at an instant said a median was a ceiling rather than a blend; and the job object's RSS moving 1.79 GiB while machine headroom moved 1.69 said neither was losing sessions nor counting strangers. Cheaper than a repeat and it catches a different class of error — a repeat tells you the number is stable, two routes tell you it is the number you meant.

  **A rearrangement is not a route, and it agrees to the last digit.** Three ways of getting `η` on this machine — dividing a slowdown, projecting the core crossing, and dividing total throughput by a solo — came to 0.7334, 0.7334 and 0.7333, which is what algebra does when every one of them reduces to `N·d/(C·s)`. That agreement was about to be written up as a confirmation. **Before believing two routes, substitute one into the other**: if the second collapses into the first, you have one measurement and a spreadsheet. The tell is that they share an input — all three of those divide by the same solo baseline, which is the loudest term in a slowdown at 4–8% against 0.94%. (*Not* the noisiest number this instrument produces — that superlative traced to one afternoon whose background collapsed mid-run, where [the day's other three solo sets spread 3.9–8.4%](docs/measurements/2026-08-02-221853-the-noisy-baseline-was-one-noisy-afternoon.md).)

  **And a pair that collapses cannot catch a rounding in what it shares.** `N·d/(2η)` and `C·s/2` are one identity here, so the machine's required core count has exactly one input and nothing in the arithmetic can disagree with it: `η` rounded from 0.81703 to 0.82 put the sizing at 16.4 where it is 16.52, below every session weight's own figure, and 16.4 rounds down to a sixteen-core box where 16.52 does not. **Carry full precision into anything whose routes you have just proven identical** — the agreement you were relying on is not looking.

  **And when one run supplies a figure, put it beside the other runs before building on it.** A solo set spreading 25% became *the noisiest number this instrument produces* in six documents, motivated two designs that avoid it, and costed a third at nine repeats a side. [Three other sets the same day spread 3.9–8.4%](docs/measurements/2026-08-02-221853-the-noisy-baseline-was-one-noisy-afternoon.md), and the loud one is the only run whose background collapsed mid-run — a solo takes a disturbance at full strength where a hundred sessions divide it. The tell is a number that arrives once and is cited as a property. **The four sets existed all day; the check was one table.**

  **And a second route is not only for agreeing — sometimes the first one cannot tell two answers apart.** A solo hold measures exactly what it claims to, and this box's low solo readings turned out to come from two different states: [9.752 and 9.801, half a percent apart, on machines whose hundred sessions ran 246.4 and 902.8 units/s](docs/measurements/2026-08-03-173452-the-slow-state-flatters-the-gate.md). They push gate M1's slowdown opposite ways — 3.958, and a 1.54 that *passes* a condition asking for 2. No number of repeats separates them, because the ambiguity is not noise. **So before trusting a fingerprint, ask what else produces the same reading** — and note which instrument got picked: the solo is two minutes and the hundred-session hold is fifteen, so the cheap probe became the one of record and the decisive one sat unread in nine artifacts. The tell is a quantity that names a *cause* rather than reporting a value.

  **The same substitution catches a requirement that is really a restatement.** *Gate M1 needs about nineteen logical processors* was derived as `N·d ÷ 2η`, and `η` here is `N·d ÷ (C·s)`, so the requirement reduces to `C·s/2` — sixteen cores times this machine's own slowdown, halved. **The slowdown then turned out to be 2.0654 rather than 2.301** because that hold lost the machine for 18% of its window, so the requirement is 16.4 cores; the point survives the correction unchanged, which is what makes it a point about the derivation rather than about the number. It reads as a fact about the gate and is a fact about this box. **A threshold computed from a quantity measured on the thing being judged is not a threshold**, and the giveaway is that the substitution leaves the subject's own numbers on both sides.
- A number that contradicts the plan rewrites the plan, never the other way around.
- **A conclusion drawn from a stand-in is a conclusion about the stand-in.** M0 spent a day establishing that memory had orders of headroom and cores were what bound the machine. Both were true of a workload holding 20 MiB and [false of an engine holding 1.69 GiB](docs/measurements/2026-07-31-022200-an-unreal-session.md), which reversed which condition trips first. Synthetic workloads exist to isolate one variable, and the moment their answer gets quoted as a fact about the real thing, name the workload in the same sentence.

  **The stand-in is sometimes the machine's own state.** A noise floor of 9.1% measured over twelve holds was about to be read as this workload's floor and applied to a rested box, where the figure of record is 4.54%. Half of it, from a machine that was not in that state. **A spread is a fact about the state it was measured in**, so before carrying one across, ask whether the machine was the same machine.

  **And on a box that wanders, any comparison across windows varies time as well as the thing you meant.** Twice in one hour: *a neighbour costs the solo baseline 27%* compared crowded holds against quiet ones taken hours apart, and the eight holds that finally varied tenancy **inside five minutes** found nothing — slope +0.151 units/s per core, r² 0.17, with 17% of spread at near-identical tenancy. Then the correction repeated the mistake, putting *a 30-second hold reads 35% higher* on ten holds from one window against fifty-two spanning the whole day; nearest-in-time it is about a quarter. The tell is that the two groups were **gathered in different sittings**, which is invisible in the numbers and obvious in the timestamps. So vary the thing inside one window or say the comparison is confounded — and note which survives: a *direction* usually does, which was enough to fix the script, while the *size* does not.

  **The stand-in is sometimes the window rather than the workload.** *The daemon is 2% of what it holds* was measured at twenty-five seconds with its buffers nearly empty; filled, the same daemon reads 5.8%. Neither figure is more correct — they are different states of the same thing, and the sentence named only the daemon. And a ratio is a fact about a pairing before it is a fact about either side: against nine real sessions that same daemon is 0.16%, so **what travels is the absolute — 363 KiB a session held — and the percentage travels nowhere.**

  The same holds for rules rather than numbers: **an invariant only exercised by things that cannot break it has not been exercised.** [The workload contract](workloads/README.md#the-contract) forbids shared paths and the ramp handed every session one directory, which three synthetic workloads never noticed because each names its files uniquely. The contract was correct and unenforced for as long as nothing needed it. **So break a new check once, on purpose, before trusting it** — the documentation-map test was shown naming `coggyd` with its row removed, `--locked` was shown refusing a lockfile missing that crate, and a solo control that could only ever report +0.0% was caught by two console lines that could not both be true. A check whose failure nobody has seen is a check nobody has read.

  **A measurement has the same failure, and it is quieter.** Three solo holds of `ping` returned 23 units each — flawless reproducibility from a workload that emits one line a second whatever the machine is doing. The same three with `cpu-spin` gave 585, 590 and 606. `ping` is the obvious thing to hold a hundred of while checking that sessions start and stop, and its unit count is elapsed time wearing a work rate's name. **Before believing a number that did not move, ask what would have moved it.** The same property is useful pointed the other way: because `ping` is a clock, [a hundred of it emitting 1.04 lines a session a second](docs/measurements/2026-08-01-163935-what-the-harness-says-about-itself.md) is a check on the session count and the window rather than on the machine.
- **A paragraph replaced leaves its summary behind.** The same edit that withdraws an explanation usually leaves the sentence restating it a few lines down, and both then sit in one file disagreeing: a README kept *lifetime, output and identity* after two sections were added, and a record kept *sessions more alike than an engine's* one paragraph after that reading was retracted. It is the counting rule's sibling — **when you change a thing, search the file for the sentence that describes it.**

  **The densest version sits in a record's own limits list, and it is what an append usually answers.** Three in one day, all in records written that morning: *the counter that would test it is the parked-core count, which nothing here records* — measured and eliminated an hour later; *the size is not yet known* about a gate exposure that was then shown not to reach the gate's figures at all; and a bullet still naming core parking as the candidate while the section directly above it ruled parking out. A "What this does not establish" section is where you write down what you could not reach, so it is exactly what the next hour's work reaches. The candidate set is too large to automate — every negation in every limits list, against three known instances from one unusually dense day, which is the arithmetic that [rejected the other alarms](#measure-before-you-optimize). What is left is proximity: **when you append to a record, reread its limits list before you commit.** One file, already open, at the moment you are editing it.
- **And a record that grows leaves its citers behind**, which is the same shape across files rather than within one. A fifth reading moved the engine figure to 1.87 GiB ± 6.4%; ROADMAP and the measurement index went on quoting the 1.865 that four readings gave, because appending to a log is correct and nothing points from the log back to whoever quoted it. [A test now refuses a decimal quoted inside a link that its target does not hold](sessionbench/tests/docs.rs) — so what is left to you is the integers and the prose. **After appending to a record, grep the repository for the figure you superseded.**

  **And grep its spellings, not its digits.** That was done for `9.144` and found four citers; the same value was also written `~21.5`, *the high teens to about 21*, and *about 21* in five more places, none of which a search for the new number reaches. Six sites, four still stale hours after the figure moved, each fixed whenever its particular wording happened to be on screen. **A number written more than one way is updated one way at a time**, so collapse the spellings to one as you go — and **when a claim is withdrawn rather than a figure corrected, grep the figure it rests on rather than the sentence.** *The thermal zone reads 39.1 °C in every artifact whatever the load* lived in three places; a grep on the sentence found the code, and the record and CLAUDE.md were paraphrases that only `39.1` reached. A withdrawn claim survives wherever it was restated in someone's own words, which is everywhere it mattered enough to repeat — it makes the next change a single search instead of a hunt for phrasings you have to remember you used.

  **That works when the withdrawn claim rests on a distinctive figure, and some do not.** *The noisiest number this instrument makes* is a **ranking**, withdrawn on 2026-08-02 once the day's other three solo sets came back at 3.9–8.4%; the figure under it is a spread of 25%, which is not distinctive enough to grep. Six documents were fixed one wording at a time, and **five more instances were still standing nine days later** — two of them living, including the two-routes paragraph in this file. Only the phrase reaches them, and phrases get paraphrased, which is why they survived a rule written for exactly this. So the two searches are complementary and neither is sufficient: **grep figures for corrections, grep phrases for withdrawals**, and expect a withdrawn superlative to keep turning up.

  **The test only sees numbers, and a link can be wrong without one.** A sentence pointing at ROADMAP's M1 section for a claim about measurement allowances resolved cleanly — the anchor exists, so both link checks passed — and the target says nothing on the subject. That was written hours after the same defect was swept for and covered by a test, which is the honest limit of the test: **a citation carrying no figure is checked by nobody but you.**

  **That limit was measured rather than estimated, and no third automation is coming.** Of 372 citations of a measurement record, **129 carry a figure** and are checked; 45 echo the record's own title, which asserts nothing; **198 make a claim with no number in it**. A gate firing on 198 is a gate nobody reads — the same arithmetic that rejected [a looser anchor check](sessionbench/tests/docs.rs) at seven suspects for one defect, and a commit-shape alarm at 18% for a 9.3% class. **Every one of those rejections was made on its own numbers**, and the count sentences below joined them the day this paragraph was written. A fifth followed from sweeping the unchecked ones: of **43 anchored citations carrying no figure** in the living documents, exactly one was wrong, and it was positional — *the second integrity rule*, pointing into a list another file describes as growing. A test for ordinals in link text is the obvious catch and fires on 21 candidates, nearly all of them titles and time spans, for that one. **The narrow shape is real and the regex for it is not.** What is left is the habit, and it belongs at the moment of writing rather than in a sweep: every citation that went wrong in that sweep went wrong in a sentence being written, and the three that were caught were caught because putting a figure in the sentence meant opening the record first. **Cite with a number when there is one** — it converts your sentence from the unchecked 198 into the checked 129, and it makes you read the thing you are citing.

  Four of those in one day, all the same shape: the right *document* and a plausible-sounding *section*. `#fixed-contracts` sounds like where a contract rule lives; the rule was in the workload contract. Guessing is what happens when the alternative is opening the file, so make the alternative cheap — `grep -n "^#" <file>` lists every heading in one line of output, and reading the section you are about to cite costs a second more. **Pick anchors from a list you are looking at, not from memory of what the document probably calls it.**
- **A sentence that counts a list will outlive its accuracy.** *Three accident modes*, *eight findings*, *those three rules*, *a session's lifetime, output and identity* — each was written beside the list it describes and each went wrong the next time the list grew, usually in the same change that grew it. The [map-completeness test](sessionbench/tests/docs.rs) catches a missing component, not a stale tally inside a page. So name the list or describe it, and leave the arithmetic to the reader who can see it.

  **Swept once, in both places, and it does not want a third automation.** Thirty-six count sentences across the living documents — every `.md` outside `docs/measurements/` and `bench-out/`, which is nine files and not the six this sentence claimed until it was checked: **two wrong**, both inside the pair of paragraphs the change was already editing, plus one that undercounted the workspace's crates. Twenty across `coggyd/src` and `sessionbench/src`: **none wrong**. The difference is not care — every code comment here counts something enumerated within a few lines of it, an `enum`'s variants, a function's arms, its own bullet list, so a change that grows the list puts the sentence in the same diff. The two that went wrong were summarising conditions scattered across paragraphs. **So distrust the count whose list is not visible from where the number sits**, which is a property you can see while writing it — and this paragraph is the demonstration, since *six* was written here, in a paragraph about counting, without opening the directory. The two files it silently excluded were then swept and came back clean: the root README's *three things* names its three in the same sentence, and `coggyd`'s *what is not built* still matches the tree, governor, audit surface, socket API and the unclosed suspend window alike — and a sweep returns about one defect per seventeen sentences, found where the editing already was.

### Treat the machine as a variable

**Check the plug before the numbers.** A hundred sessions at duty 0.27 gave 907 units/s on mains and [135 seven hours later on battery](docs/measurements/2026-08-02-195840-the-same-command-on-battery.md) — 7.8×, from the same command with every other recorded figure identical: same session count, same RSS to a hundredth of a gibibyte, a steady climb rather than a stall, and a thermal zone at 42 °C. A run that is merely slow produces a clean artifact, so nothing looks wrong until a figure is set beside one from the other state. `doctor` says which state it is in and every artifact now carries it, which is what makes this a check rather than a thing to remember.

**Four scales, and only the smallest supports a comparison.** The power state is worth 7.8×; **the thermal state is worth 2.2× on a solo rate and 72% on a slowdown**; one run against another in the same state is worth up to 14%; one hold against another inside a run is worth 0.4% to 1.5%. So a claim built on two holds of one run stands, a claim built on two runs needs their fingerprints to agree first, and a claim across a power state is not a claim. The gap is also why the largest one hid for a day: a figure carrying it does not read as a noisy version of the other state, it reads as a measurement of something else entirely. **And the power state is not merely the largest multiplier — a ratio does not survive it, where a ratio survives every other handicap here.** The rule below is that a comparison dividing one hold by another hands both the same disadvantage, so a steady background leaves the shape of the answer intact. The plug does not work that way: the same tenancy comparison runs [+60.9% on mains and −5.2% on battery](docs/measurements/2026-08-11-173433-the-tenancy-step-is-on-mains-and-absent-on-battery.md), so an effect that is real in one state is **absent** in the other rather than smaller. That is what makes it the one variable a null result cannot be reported without — the sweep that found nothing had found nothing *about battery*.

**The thermal one is the same shape and hides better, because nothing reports it.** `doctor` names the power state in every artifact; nothing names this. [This box's solo rate halved and stayed halved for about ninety minutes](docs/measurements/2026-08-03-004512-a-saturating-burst-halves-the-box-for-an-hour.md) — flat before, flat after, two steady states rather than a decay — and a whole gate bracket ran inside the slow one without anything looking wrong. **What causes it is narrowed to a duration.** Deliberate bursts of three and twenty minutes at a fixed duty both failed to induce it; forty-one minutes did, on the night the machine also stopped dead — **and that run held `--wait-ms`, whose duty climbs as the box slows**, so the two differ in profile as well as in length. The threshold sits between twenty and forty-one minutes of saturation, the state lasts about ninety, and testing it means running the load that ended in a hard stop — which takes any session-scoped scheduler with it. **Neither the ACPI thermal zone nor `% Processor Performance` can tell the two states apart on this box**, and both were tested rather than doubted: the zone read 39.1 °C in every artifact for a week and 63.1 °C in every artifact on 2026-08-11, so it moves between days and never within one — and predicts nothing either way, since solo holds under 50 °C average 12.422 against 12.634 over it and the box was slow and loose at 40.1 °C with its cores boosting at 175.6%, and a before-and-after pair of the clock ratio went 171%→154% on an idle session and 159%→200% under a hundred, the loaded one rising. What identifies the state is **not** a solo hold's own rate, which is what this said until two runs were set side by side: [solo holds agreeing to half a percent, 9.752 and 9.801, held a hundred sessions at 246.4 and 902.8 units/s](docs/measurements/2026-08-03-173452-the-slow-state-flatters-the-gate.md) — one box crippled under load, one 0.5% from its rested reference with only its lone session down. They move the gate's slowdown in opposite directions, 3.958 against 1.54, so the same fingerprint reads as failing by 98% or passing outright. **Most of that pair is now attributed to the tenant, from a field both holds already carry.** Across the seven hundred-session mains holds with a rest column, per-session rate against cores held elsewhere runs [r = −0.950 at a slope of −0.4889](docs/measurements/2026-08-11-085752-the-neighbour-helps-one-session-and-robs-a-hundred.md), a fitted 829 units/s total at half a core held against 267 at twelve — while the same tenant moves a *solo* hold **+34% the other way**, so tenancy raises the numerator and lowers the denominator and the slowdown compounds: 1.255 with both arms quiet against 4.959 with both tenanted. **So read `rest_cores_median` on both holds before reaching for a reference throughput** — it costs nothing and is already written, where a hundred-session reference costs fifteen minutes. It narrows rather than closes: a lone session at 9.0 against a rested 18.9 with 1.03 cores held is worth 2× with no neighbour present and stays unexplained. **A concurrent hold's own throughput separates them too**, and every run already records it. **Read it beside the rest column, not alone** — a hundred sessions held against a tenant came back at 344.9 units/s with 8.56 cores held elsewhere, landing inside the 3.1x gap that nine *quiet* holds had left empty — and then a tenth **quiet** hold landed there too at 756.1 with 0.49 cores held, the lowest ever recorded, so the gap was a fact about nine readings rather than about the machine. Throughput says how much the box is producing; the rest column says whether anything else is taking it. A solo hold says something is slow; it takes a hundred sessions to say what. What catches it is the bracket's own solo rungs, which is why [the one time they disagreed by 53% the run was refused rather than published](docs/measurements/2026-08-03-003443-the-footprint-result-was-the-machine.md) — and why a pair of *before* rungs agreeing tightly proves nothing about which state they agree in.

A long session of back-to-back ramps makes the box slower, and a slower box is not a different mood — it is a different machine, so late measurements stop being comparable with early ones. This is measured rather than suspected: **a rung that ran 40.02 units/s at the start of one ramp ran 38.11 at the end of it, 4.8% down**, and that alone dragged the fitted redline from ~33.6 to 32.3. That 4.8% is the *gradual* version, and it is the small one — the state change above arrives in three minutes and is worth 2.2×.

Every ramp now repeats its lowest saturated rung at the end and reports the gap. **Read that line before quoting anything else in the run.** Past a few percent the redline is reading low and the run is a draft.

**That control covers one ramp, and most claims here span two.** Pipes against pseudoconsoles, `cmd` against `pwsh`, one duty against another — each sets two ladders side by side and assumes they saw the same machine. A pseudoconsole ramp ran nine hours after its pipes counterpart and its solo session was **half the speed**, which no drift check could catch because both ramps held still internally. **Two ramps whose solo rungs disagree are not comparable** — and the converse does not follow, which is the correction this sentence needed: it read *two ramps are comparable when their solo rungs agree* until [two quiet holds ninety minutes apart agreed to 2.6% across a power state worth 7.8×](docs/measurements/2026-08-11-163342-a-solo-baseline-cannot-see-the-plug.md). The ceiling binds under saturation and a lone session at duty 0.27 asks for a quarter of one core out of sixteen, so the fingerprint has no signal on the largest variable the machine has. Agreement proves the box is not in the **slow state**; it is silent on the plug, which is a boolean in every artifact and which `compare` now refuses a pair for crossing. The rung is still a fingerprint for what it was built for — one session, no contention, the same work — and comparing redlines whose fingerprints differ measures the afternoon. `sessionbench compare` refuses the pair and exits non-zero. Run a comparison back to back or not at all.

**When a measurement will not fit the machine, shrink the measurement before blaming the machine.** A ten-session cook ramp needed 19 GiB against 8.7 free and was written up as blocked; four sessions answered the same question twenty minutes later, because aligned peaks would have shown 20 GiB and nothing came within a factor of two. The narrow memory was a condition rather than an obstacle — wide enough to leave the signal intact, narrow enough to make alignment visible. Reach for the smallest design that can still be wrong in the way you care about.

Whatever you watch a run with must emit a per-rung line, not only its verdict. A watch filtered down to redlines and failures cannot tell a working run from a hung one, and that ambiguity gets settled by reaching for the box — which is the one thing forbidden below.

**Ask what this machine can still answer before calling the window shut.** A loud box spoils *work rate*, which is the whole of a redline's noisy half. It barely touches RSS — an hour-long hold said so in its own opening line — and it touches a teardown less still, because processes leaving is not work being done. A day spent waiting for quiet had the graceful teardown at a hundred sessions available the whole time, untested, and it took fourteen seconds at 48% background. **A window is shut for a quantity, not for the afternoon.**

**And a ratio wants a steady machine rather than a quiet one.** The threshold above is written for an absolute work rate. A measurement that divides one hold by another hands both the same handicap, so a background sitting at a steady 40% leaves the shape of the answer intact — while [one *swinging* between 5.07 and 6.97 cores over a minute](docs/measurements/2026-08-01-163935-what-the-harness-says-about-itself.md) puts ±16% into a comparison chasing 6.9%, and every hold sees a different machine. **But `doctor` invocations are not that swing, and using them as a proxy costs runs.** Four consecutive readings spreading 26.7% were read as a shut window and nearly cancelled the hold that answered gate M1's last open question; [the bracket that followed spread 0.28% and is the quietest this instrument has produced](docs/measurements/2026-08-03-000430-the-footprint-lever-runs-backwards.md). The ±16% above was the harness's own sampler across one run, and a two-minute solo hold averages over a swing that four point readings sample. **So do not pre-screen a ratio on the background at all — the bracket refuses itself when its baselines disagree**, it reports the standard error it refused on, and that is a measurement of the thing that matters rather than of the thing next to it. **It fails in the other direction too, and that one costs the run rather than the afternoon.** A reading of 1.89 cores approved a window in which [a tenant then took 11.5 of 16 for two of three back-to-back solo holds](docs/measurements/2026-08-03-070018-a-solo-triple-spread-thirty-percent-and-the-column-said-why.md), spreading them 30% while the job never moved. So the instrument over-warns on a fine machine and under-warns on a bursting one, which is one instrument being asked for a window when it can only give an instant. **The bracket does not cover this by itself either** — two baselines inside the same burst agree with each other and are both wrong, which is the failure mode agreement cannot have an opinion about. What answers it is the run's own rest-of-machine figure, `(machine_cpu_percent - cpu_percent) / 100`, which every hold now records beside the job.

  **And the baseline has to bracket the run rather than precede it** — [two solo triples ten minutes apart differ by 8.5% where each spreads under 3.5%](docs/measurements/2026-08-01-163935-what-the-harness-says-about-itself.md), so drift between runs is three times the noise inside one.

**And `rest_cores_median` cannot tell you what is holding the machine, by construction.** It is `(machine_cpu_percent − cpu_percent) / 100` — a subtraction, so it is an anonymous residual: it can say ten cores are held elsewhere and never by what. Every hold in the tenancy investigation carries that column and none of them could answer a question that took one query. The census counter cannot answer it either, summing only instances above half a core. **What answers it is diffing kernel `TotalProcessorTime` per process across a window**, which neither misses load spread thin nor loses load concentrated in one place — and which named this box's ten-core disturbance as [Playwright's headless Chromium doing SwiftShader software rasterisation](docs/measurements/2026-08-12-045500-the-anonymous-neighbour-is-a-software-rasteriser-and-the-observer-is-bigger-than-the-treatment.md), agreeing with `doctor` at 12.51 cores against 12.40. **So when the identity of a neighbour matters rather than its size, it is one query and it belongs beside the hold** — and a cost measured against that neighbour is conditional on it: *while this box runs Playwright* is a different claim from *this machine cannot*.

While a measurement is running, do nothing else on this machine — no builds, no `git`, no `gh`, no file edits. The observer is not free. [The Defender estimate](docs/measurements/2026-07-30-142218-defender-at-scale.md) was wrong by two orders of magnitude partly because `gh` ran during the run that produced it, and the drift figure above came from a ramp with edits happening alongside it.

**And the rule now has a figure, which is larger than the thing most experiments here inject.** Attributing every process during a solo hold, [the agent held 1.64 cores against the measured session's 0.20](docs/measurements/2026-08-12-045500-the-anonymous-neighbour-is-a-software-rasteriser-and-the-observer-is-bigger-than-the-treatment.md) — more than the ~1.3 that six `cpu-spin --duty 0.27` co-tenants contribute. **So an agent working alongside a hold is a larger neighbour than the neighbour under study**, and it enters `rest_cores_median` anonymously, where nothing can tell it from the browser. It is a WORKING cost and not a footprint: the same two processes read 0.04–0.17 cores idle, minutes apart.

**The consequence is sharper than contamination, because it can make a run report the belief that caused it.** A gate waiting for the machine to fall under one core cannot fire while the observer holds 1.64, so a waiting run times out with `gave up without a quiet window` — which reads as *this box does not go quiet* and is indistinguishable from the machine being busy. The failure confirms itself. **During a waiting run the requirement is idleness rather than light work**, and the difference between 0.04 and 1.64 cores is the difference between the gate being able to fire and not.

Between runs, keep the footprint from accumulating:

- **Prune `bench-out/`, once the record exists.** Each ramp leaves roughly 500 files, all on the scanned side of Defender's line, and thirty-five of them once reached 7 GB. Keep the newest run or two. It is gitignored and nothing committed points into it, which is exactly why an unwritten run has its only copy there — the record is the artifact, this is scratch. **The size is a ramp's, and a hold is not a ramp.** Seventy-three one-session holds came to 17 MB, three orders below the ramps this rule was written for, and keeping them paid: [a task closed because a run from two days earlier still had its six solo baselines on disk](docs/measurements/2026-08-03-094550-the-slow-state-caught-on-a-quiet-machine.md) to read against bands that did not exist when it was taken. So prune by what is actually large, and let cheap artifacts accumulate — an old hold is a comparison you have not needed yet.
- **Check for survivors** before trusting a run — `Get-Process cpu-spin,file-write,stdout-storm,sessionbench`. Teardown reaps its own scratch and its own sessions, and has been verified to leave nothing, but a killed ramp is a different story.
- **Do not reach for `cargo clean`.** It buys back a few GiB and costs a full rebuild, which is the slow thing the cleanup was supposed to fix.

## Verify before you report

Running `cargo build` proves the code compiles, which is not what anyone asked. Run the thing, read its output, and check the output against something independent.

**A check has to measure the thing it is checking**, and the cheapest way to get this wrong is to read whatever is nearest. Four in one day, each answering confidently from beside the instrument that decides:

- **The console is not the report.** A run streams progress and then writes a record; a rung line printed mid-ladder can be superseded and a refine pass revisits counts that looked settled. Two findings built on streamed lines were withdrawn when `ramp.json` disagreed — one a process-count anomaly the finished report showed as exactly 2.00 per session on every rung. Watch the console to know a run is alive; quote nothing from it. **And a report still being written is not the report either.** In an hour-long hold sampled every five minutes, one window's growth rate was called a constant, then three windows were called a deceleration with a mechanism attached, and a fourth window 58% higher killed both — while the whole-span figure agreed with the segment mean the entire time. The tell is deriving a rate, a slope or a ratio from consecutive samples while more are still arriving. And the number all of that was extrapolating toward gets *measured* two samples later, which is the point: **do not model what the running measurement is about to hand you.**

  **The same shape sits between runs, where the data is complete and the window is not.** Three times in one day a level was written up from a finished, sufficient set and killed by the next reading: twenty holds flat across 340 minutes, then 15.216; three holds inside 2% at 10.5, then 9.7–10.1 half an hour on; eight consecutive windows inside 1.0 units/s for an hour, then 12.638. Nothing was mid-flight and no sample was missing — **what was too small was the span, not the sample.** So a stability observed over one window is a fact about that window until a later one agrees, and the way to find out costs one more reading rather than an argument.
- **A point sample is not a windowed mean.** A watcher waiting for `doctor` to call the machine quiet sampled instantaneous CPU instead, reported 8.4% and called it quiet while `doctor` read 23% of the same minute.
- **A frequency heuristic is not an efficiency class.** The pure-Rust way to find hybrid cores groups them by observed clock, and clocks converge on an idle machine — which is when `doctor` runs, so it would report one tier here and be believed.
- **A total is not its largest part.** A record's *Peak total RSS* of 624.9 MiB was quoted as the daemon's, which made a workload's line length look like a 14× lever on it and opened a whole axis to go measure. The same record states the daemon's actual cost two tables down at 363 KiB a session — and the arithmetic refuses the misreading outright, since 2000 lines × 100 sessions × 130 B cannot reach 625 MiB. **A figure lifted from a table takes the table's row label with it**, and *total* is the label most easily dropped.
- **A link checker is not GitHub.** Collapsing runs of spaces where GitHub replaces each one reported 23 sound anchors as broken; every one would have been "fixed" into an actual break.

**And a filtered console is not an exit code.** A `cargo test` run was piped through a pattern meant to catch failure names, the pattern missed, and every line that survived said `ok` — so a red run read as green twice. It was red for two unrelated reasons at once: four of `coggyd`'s twenty-four lib tests failing at 98% background, and a measurement record missing from its index, one of which recovered on rerun and one of which did not. **Reading the survivors of your own filter is reading a question you wrote, not an answer** — the exit code was 101 throughout and said so. It is the observer rule's sibling: silence is what a healthy filter and a broken one both produce.

  **So it is a procedure rather than a caution, because the caution failed twice more the same day it was written.** Send the whole output to a file and search the file — `L=/tmp/t-$$.log; cargo test > $L 2>&1; echo $?; grep -E "test result|FAILED" $L`. **Give the file a unique name**, which a fixed one cost on 2026-08-11: two gate runs overlapped, the second's redirect failed because the first still held the path, `cargo test` captured nothing, and `$LASTEXITCODE` reported the **0** it had inherited from the clippy call before it. A zero that is not evidence, a filter that matched nothing, and a status belonging to another command, all at once — and the only tell was the shell printing its lock error into the same stream, which is luck rather than a check. The full text survives, the exit code is the command's own rather than a pipeline's last native member, and a pattern that matches nothing leaves a file you can open instead of a screen you cannot distinguish from success. Three runs today were read wrong for want of this, and the third produced no result at all and reported zero. **And the bill for one of them came to nine days.** The filtered run was the only sighting of an intermittent test failure; its four names went into the pattern and did not come out, so what survived was *four of coggyd's tests fail at 98% background* with nothing to debug. Five conditions were then ruled out one at a time — 87%, 88% with a cold build, 92% twice, 99%, and full self-saturation — and the hypothesis was written off as spent. It reproduced on the next gate run at 95%, named itself in one line, and was [a fixed 900 ms sleep waiting for a process to exit](coggyd/src/pool.rs). Every earlier pass was that sleep happening to be long enough. **The whole investigation existed because the first sighting was filtered**, and it would have been a ten-minute fix.

**And a zero exit is not evidence of work.** Things that reported success while doing nothing: `cmd` handed a mangled switch printed three error lines a second and the ramp counted them as units; `timeout /t` returned instantly without a console and a supposed idle loop spun fifty times a second; `waitfor` rejected a hyphen in a signal name by exiting at once with status 0; a control compared a figure with itself and reported a perfect 0.0%; a failed job assignment returned an error while leaving the process running; and a PowerShell script refusing to run on an unusable machine said `exit 1` and reported 0, because piping its output makes `$LASTEXITCODE` the last *native* command's. The first five are other people's tools and the sixth was written an hour after reading this list, which is the more useful half of it. **Assert on the effect, not the status** — a file that appeared, a count that moved, a process that is still there. **And that cuts both ways: a non-zero exit is not evidence of the failure you wanted either.** A test was planted with a deliberate defect, the run exited 101, and the 101 was read as the gate catching it — it was a compile error, because the test being added already existed twenty lines up. The tell was there and was stepped over: the filter printed *nothing*, no `test result`, no message, which is what a run that never reached the tests looks like. **A check you are breaking on purpose has to name the thing it caught**, and reading its message rather than its status is what separates a working gate from a broken build.

**And in data, the same shape is a zero where a quantity does not exist.** Building one measurement path for a second kind of target met it four times in a day: a report line missing its unit count, a drop count nobody could take, a daemon that had not spoken yet, and an output-byte figure that had no source. Every one had `0` as the obvious value, and every one would have passed — zero drops satisfies a condition whose tolerance is zero, zero units reads as saturation, zero bytes says a hundred sessions produced nothing. **Make the type carry the absence**, and the check will not accept it by accident.

  **A sentinel is the same defect wearing a different number, and it inverts when you edit it.** A waiter for a quiet machine returned `99` cores when the counter could not be read, which was safe by accident — 99 sits on the busy side of every threshold. Changing it to `-1` so the transition log would stop recording a failed query as a twelve-core neighbour was correct for the log and silently inverted the gate: the test is `cores -lt limit`, and −1 is less than everything, so an **unreadable counter became the quietest possible machine** and would have fired the run it exists to withhold. Nothing failed — the script parses, runs, and is confidently wrong — and what caught it was reading the branch order straight after the edit. **So a sentinel must not be comparable to the quantity it stands in for**: `None`, a second return value, anything the comparison cannot silently accept. And when one is unavoidable, the branch that tests it comes first, with a comment saying the order is load-bearing.

The fourth had a different answer, which is the part worth remembering: the number existed and was not reported. **Ask whether the quantity is really absent before wrapping it in an option** — for that one the fix was one `+=` in the daemon, where an `Option` would have marked an axis permanently unmeasurable.

  **And the same field lies the other way round when you read it.** A tally excluded two artifacts because their `hold.json` had no `rest_cores_median`, the field being younger than they were. One of them carried the underlying samples at the corrected scale and its rest was one `jq` away — recovering it moved the headline share by 80%, from 2.4% to 4.4%. **A `None` means this artifact does not store the value, never that the value cannot be had**, and the check is arithmetic on what is stored rather than the file's date: a machine-wide reading under one core while a session runs is the old scale, whatever the timestamp says.

  **And the same absence hides in a column that is written but never read.** A whole-machine CPU figure was added, written to every sample for four runs, and stored on a sixteenth of the scale of the column it exists to be subtracted from — so [the job read as larger than the machine it ran on in 31 of 36 samples](docs/measurements/2026-08-03-061911-the-machine-column-was-narrower-than-the-job.md) and nothing objected, because the subtraction it was added for had not been done yet. A number nobody consumes has not been measured, whatever its units say. **So take the difference the column exists for on the first run that has it**, even when the run was for something else.

  **A fifth instance moved the axis from values to processes.** A sampling loop asked its watcher for numbers and never asked whether the thing producing them was still alive; a daemon exiting at five seconds of an hour would have given fifty-nine minutes of empty samples and a session count frozen at its last report. **Something that stopped reporting looks exactly like something reporting the same thing** — so a loop reading a subject has to ask after the subject, not only after its numbers.

  **And a second loop had the same hole**, found hours later. Two sampling loops in two files each read a daemon and neither asked whether it was alive; fixing one is what made the other visible. **When a fix is for a shape rather than a line, grep for the shape.** The tell is a fix whose commit message describes a category — an absence reading as a value, a stopped thing reading as a steady one — and the fix touching one call site.

  **Having the rule did not fire it.** A commit teaching the daemon to count failed reads wired one of two entry points; three doc comments and a README row went on saying two of the four gate conditions were out of reach, and the README was then edited to say three, which made it claim something the ramp does not do. That is the rule's second miss, and the first is what wrote it.

  **So it was measured before a third rule was written on top.** 28 of 300 commits — **9.3%** — exist because an earlier change left something behind, and the rate is steady: it was 9.1% at 254, and the 46 commits since include a night of unusually dense correction work that did not move it. So this is a property of how the work goes rather than of one stretch of it. The obvious alarm is *category language in the message* plus *one source file touched*, which fires on 18% of commits, and most of the 9.1% is a document trailing code rather than a second call site, so it would not even be looking at the right thing. It was [rejected like the others](#measure-before-you-optimize). **What is left is the habit, and the habit is cheapest at the moment the commit message is written**: if the message names a class, the diff should show more than one place, or say why one is all there is.

**The tell is a confident answer from an instrument nobody checked against the one that decides**, and the adjacent instrument is always the convenient one. When several things look wrong at once, suspect the check before the subject — one place being wrong is usually that place, many places being wrong is usually you.

Before saying a change works:

```
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
cargo +1.88.0 check --all-targets      # the declared MSRV, which the tracking toolchain never exercises
cargo run -p sessionbench -- doctor    # and read it
```

And for anything touching `coggyd` or the code that drives it, [the three coupling examples](sessionbench/README.md#running-it) come before the measurement — `cargo test` compiles them and runs none, which is a choice that README explains and a gap this list would otherwise hide.

When an independent check disagrees with the code, suspect the check first — but say so either way. [CONTRIBUTING's accident modes](CONTRIBUTING.md#the-one-rule-that-matters) are each a real mistake made in this repository.

### Verify before you launch, too

Two ramps in one afternoon measured nothing, and both were launched from a parameter that was never read back from whatever would consume it.

- `--max-sessions 40` fell between the ladder's own steps of 25 and 50, so it could not bracket and returned a floor. Those steps are a constant in `redline.rs` that nothing stopped anyone reading first.
- `cmd /c` arrived as `cmd C:/`, because Git Bash rewrites a leading-slash argument as a Windows path. Every session died instantly, the shell's error lines were counted as completed units, and four rungs came back "held" at zero bytes resident. `ramp.json` records the argv it really spawned.

**A smoke test written beside the script does not cover the script.** The one that passed here used `cmd //c` — differing from the real command in exactly the character that was broken, so it confirmed a shape nothing would run.

So for anything that will occupy the machine for more than a rung: read the parameter back from the code or the artifact that consumes it, and pre-flight the real command shape. A twenty-second `observe` that prints the recorded argv costs a six-hundredth of the ramp it protects.

## Stay inside the open gate

One question decides whether to start any piece of work: **does this move the number on the gate that is currently open?** If not, it belongs to a later milestone.

Consequences that are easy to miss:

- **Order holds inside a milestone too.** M0 runs one session to completion *before* the ramp harness exists, because the single run is what says whether the redline conditions are pointed at the right thing.
- **Engines are workloads before they are integrations.** [M5](ROADMAP.md#m5--engine-surfaces-exploratory) is four milestones out whatever is installed, and nothing in the daemon will ever know an engine exists. But **Unreal Engine 5.8 and Unity 6000.4.7f1 are both installed here**, with Visual Studio and MSVC, so measuring against a real engine was available the whole time it was being called impossible — and [it reversed which condition binds](docs/measurements/2026-07-31-022200-an-unreal-session.md), then [showed that one engine installation builds one thing at a time](docs/measurements/2026-07-31-034150-unreal-builds-serialise.md). Blender and Godot are genuinely absent.

**This paragraph got it wrong twice, which is the point of it.** Unreal was called absent until a directory listing said otherwise, that listing became the rule above, and Unity was then left in the "absent" list by the same paragraph — unchecked for another day. Having the rule is not the same as noticing the moment it applies, and the moment is whenever a sentence is about to say a machine lacks something.
- **Check what the machine has before writing down what it lacks.** The claim above was carried through a day of decisions — it sent G0 to "blocked", picked a Rust build as a stand-in, and shaped this file. Confirming it cost one directory listing, and the cheapest moment to spend that was when the sentence was first written.

## Commits

[CONTRIBUTING's commit rules](CONTRIBUTING.md#commit-messages) are binding: Conventional Commits, one of eleven types, no co-author trailers of any kind. Commit when a change is coherent and green, not per edit.

**Read `git status` before writing the message, not `git add` from memory.** Scoping the add to the paths you edited keeps a commit focused and silently drops what the change *caused* — `Cargo.lock` sat unstaged across five commits that added a crate, so a clean clone could not build any of them with `--locked`. No local gate says so, because `--locked` compares the manifests against the lockfile on disk and that one was always current. The commit is where a generated file gets lost, so that is where to look for it.

**A run, its launcher and its watcher each have a lifetime, and every accident here came from choosing them separately.** They go wrong in both directions, and the launcher's own detachment turned out to be one of them:

- **The launcher was too short.** A gate hour started as an agent's background task, which carries a ten-minute ceiling; the probes and three two-minute baselines spent it and the run died the second the hour began. Detach it — `Start-Process ... -WindowStyle Hidden -PassThru`, **and do not redirect its output** — so the thing holding it is not something with a timeout. **The redirection is not a detail, it is the thing that kills the run.** This said "with the output redirected" for a fortnight and cost four harvests, because `-RedirectStandardOutput` forces `UseShellExecute=$false`, which makes the child **inherit the launching console** rather than take one of its own — and every process on a console gets the control event when it tears down. Three of those deaths left only absences: no `Stop-Transcript` footer, no stderr, no event, no terminal line. The fourth was launched holding the process handle, and named itself in three seconds — **`EXIT -1073741510`, which is `0xC000013A`, `STATUS_CONTROL_C_EXIT`**: a console control event, not a `TerminateProcess`. Nothing is lost by dropping the redirect, because these scripts already write their own timestamped transcript under `bench-out/`, which is the artifact actually read and which held byte-identical content every time. **A run that dies without an exit code cannot be diagnosed** — `Start-Process` without `-Wait` returns immediately and the handle dies with the launching shell, so hold it and call `WaitForExit`.
- **The launcher's cause was mis-assigned to the launcher's operator, and that made three deaths look explained.** They were first attributed to my own `Get-Process pwsh | Stop-Process -Force`, which really did kill a run — once, witnessed. One true instance covering for three others is what an attribution does when nobody measures the rest, and the exit code is what separated them: the fourth died with no kill of any kind, three seconds after launch, while the shell that started it was still sleeping. **And the survival times argue for nothing** — one lived seventeen minutes under the same defect, because when a console tears down is not something the run controls or observes.
- **The opposite mistake reaps a run nobody meant to touch — kill by PID, never by name.** `Get-Process pwsh | Stop-Process -Force` cannot tell a leftover from a live measurement, and the same command killed a test process minutes later, in front of me. Identify the process, print its start time, confirm it is the target, stop that one — which was done correctly twice that day and abandoned for the broad form as soon as it was convenient. **Killing the launcher does not stop the run either**: `sessionbench` owns the job, so stop that instead, and it reaps the tree.
- **The watcher was too short.** The five-minute stallwatch lived only in session memory, so a reboot took it while the conversation was restored around it, and nothing ran for thirteen hours.
- **The watcher was too long.** A `Monitor` armed `persistent` tailed a log whose run had finished, and sat there for thirteen hours seeing nothing. `persistent` is for a watch with no end; a run with a known end takes a bounded timeout, and **the moment you read a run's result is the moment you retire its watcher** — make that a step of handling the result, not something to remember. **That phrasing does not fire, measured on three lapses in one day.** All three were runs that ended *on their own*, or whose result was read *from the artifact* rather than from the stream — so the watcher never entered the picture: it had already said what it was going to say, or it never spoke at all. All three sat armed for tens of minutes and timed out harmlessly, which is why the habit does not correct itself. The trigger that does fire is narrower: **when you open an artifact to find out how a run ended, that is the moment**, because that is exactly when the stream has stopped being the thing you are reading.

  **And that trigger then fired correctly while a watcher survived anyway, because retiring *the* watcher assumes you know how many there are.** Two were pointed at one log; the artifact was opened, the run written up and committed, the remembered one retired — and the other announced itself by timing out half an hour later. This is not forgetting to act, it is acting on an incomplete set, so no sharpening of the trigger reaches it. Nothing enumerates armed watchers, so the set exists only in memory, which is the thing that lost it. **Write a watcher's id into the task it serves at the moment of arming**: the two that were recorded were retired, the one recorded nowhere outlived its subject, and retiring a run then means retiring every id its task names — a list you read instead of recall.
- **The turn is a lifetime too, and ending one mid-launch stops everything.** A launcher was patched and the turn ended before the relaunch: nothing ran for thirty-nine minutes, and the commit log shows it as an hour of silence in a day that otherwise committed every two to twelve minutes. **A fix that unblocks a launch is not the launch** — the enabling step feels like the unit of work and is not, which is why this ends a turn cleanly enough to look finished. The check is state rather than memory, and it is three questions at the end of every turn: **is anything running, is a watcher armed, is any task open?** Nothing running and nothing watching while work remains *is* the stall, whatever it felt like. The same shape reaches further than a turn: [a reboot took the scheduler](#commits) and thirteen hours passed the same way.
- **The watcher was bound to a path rather than to a run.** One waiting on a log file matched the *next* run's log after that file was deleted and recreated, and only by luck was it the line it wanted.

**Every one of these produces silence, and silence is what a healthy watch produces too** — which is [the same shape the daemon's drain had](coggyd/src/lib.rs), where a failed read returned on the same branch as a clean end-of-file. So the check is never *is it quiet*; it is **whether the thing that would speak is still there and still pointed at the subject**.

**And commit before any wait whose end you cannot see** — a ramp, a long build, anything measured in hours. The session that resumes is not always the process that started: one ended mid-ramp and came back seven hours later, leaving an instrument fix uncommitted and three finished ramps recorded nowhere but `bench-out/`. Everything survived, and none of that was by design. Work that exists only in a working tree or a gitignored directory is invisible the moment the thing holding it stops.
